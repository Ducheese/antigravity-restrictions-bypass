# 议题二：解除工作区规则双层字节上限与 Token 预算截断门禁

## 一、 核心现象与数学实锤

在复杂工程工作区中，工作区规范（如 `F:\Git\GEMINI.md` 或 `CLAUDE.md`，总大小约 40KB+，包含 500+ 行）被注入系统提示词 `<RULE[...]>` 时，后半部分总是神秘丢失，并在第 279 行末尾被截断出一行红字标记：
```markdown
<truncated 16465 bytes>
```

导致工作区后半部分的关键规范（底层引擎基础设施、编译约束、禁区仓库、敏感操作许可）完全无法对 Agent 生效，引发越权操作风险。

### 1. 23,753 字节截断的精确数学实锤
内核在读取规则文件时以行为单位累加字节，当发现总字节数跨越 **24,000 字节（0x5DC0）** 时，向前回溯寻找前一个换行符（`\n`）实施截断裁剪：

| 行号 (Line) | 该行内容概览 | 该行字节增量 | 累计字节数 (Cumulative Bytes) | 判定结果 vs 24,000 阈值 | 内核动作 |
| :--- | :--- | :---: | :---: | :---: | :--- |
| **Line 278** | 表格项：`H-AN-CSS-ZipLine` | 96 字节 | 23,648 字节 | `< 24,000` | 正常读取缓冲 |
| **Line 279** | 表格项：`H-AN-CSS-Slide 等` | 105 字节 | **23,753 字节** | `< 24,000` | **最终安全保留行** |
| **Line 280** | 空行分隔符 (`\n`) | 1 字节 | **23,754 字节** | `< 24,000` | 空白字符 |
| **Line 281** | `> **公共头文件规则...**` | 431 字节 | **24,185 字节** | **`> 24,000 (溢出)`** | **触发换行截断裁决** |
| **Line 282~483** | 后续规范、基础设施、编译说明 | 16,033 字节 | 40,218 字节 | `> 24,000` | 全部被截断丢弃 |

- **裁决计算公式**：
  `被丢弃字节数 = 文件总大小 (40,218) - 截断点保留字节数 (23,753) = 16,465 字节`。
- **结论**：提示词中的 `<truncated 16465 bytes>` 与内核的 24,000 字节换行裁决 100% 严丝合缝匹配。

## 二、 双层门禁数据结构与底层机制逆向

通过 IDA Pro 对 `agy.exe`（Go 编译的 Windows PE64 可执行程序）反编译，完整还原了规则注入的底层数据结构与四阶段生命周期。

### 1. 核心数据结构还原 (Go)
```go
// 截断内容数据结构（由 sub_140BB2600.String() 进行格式化）
type TruncatedContent struct {
    Prefix         string // +0x00 (ptr), +0x08 (len): 截断前保留文本
    Suffix         string // +0x10 (ptr), +0x18 (len): 后缀（通常为空）
    TruncatedBytes int64  // +0x20: 被丢弃截断的字节总数
}

// 规则项目元数据
type RuleItem struct {
    ID          string // +0x00: 规则标识符 (例如 "user_global", "F:\\Git\\GEMINI.md")
    Path        string // +0x10: 文件绝对路径
    Content     string // +0x20: 规则正文
    Type        int32  // +0x30: 规则类型 (1: User Rule, 2: Workspace Rule)
    Tokens      int32  // +0x34: 该规则独立计算的 Token 消耗量
    IsTruncated bool   // +0x38: 是否已被换行裁剪
}
```

### 2. 四阶段生命周期流程
```
                      【规则处理生命周期四大阶段】
  磁盘原始规则文件 (40KB+)
      │
      ▼
  [阶段一：文件物理加载与大小门禁] ──> 检查 Body 大小是否 > 24,000 字节
      │                                (cmp rax, 24000)
      ▼
  [阶段二：换行边界裁剪 (Newline Crop)] ──> 超额向前寻找 \n 截断，构造 TruncatedContent
      │                                (mov ecx, 24000)
      ▼
  [阶段三：总 Token 预算仲裁 (Budget Sweep)] ──> 检查规则集累计 Tokens 是否 > 20,000
      │                                (cmp ebx, eax -> 超额按优先级整条丢弃!)
      ▼
  [阶段四：系统提示词拼装与 Clamp] ──> 拼装 <RULE[path]> 标签与请求门禁钳位
```

## 三、 为什么单改任何一层都必死？

`agy` 的规则防御纵深设计了前后串联的两道硬编码壁垒：

1. **第一层：单文件 24,000 字节（0x5DC0）物理文件裁剪门禁**
   - 现场机器码：`b9 c0 5d 00 00` (`mov ecx, 24000`) 与 `48 3d c0 5d 00 00` (`cmp rax, 24000`)；
   - 行为：单文件一旦超过 24,000 字节，在读取进入内存阶段就会被硬编码打断，生成 `<truncated %d bytes>`。
2. **第二层：规则集 20,000 Tokens（0x4E20）全局总预算门禁与安全 Clamp**
   - 现场机器码：`ba 20 4e 00 00` (`mov edx, 20000`) 与 `48 81 fb 20 4e 00 00` (`cmp rbx, 20000`)；
   - 行为：在规则加载完毕计算 Token 后，对整个规则集实施总预算仲裁。
   - **第二层的惩罚是致命的整条丢弃（Drop Rule）**：若规则集合计超过 20,000 Tokens，内核会输出警告：
     `"The following user-defined rules exceeded the rules token budget and were excluded from inline injection: %s"`
     并将整条工作区规范直接从上下文排除！

**核心死锁关系**：
- 如果只改第一层字节上限：当规则文件扩充、总 Token 突破 20,000 时，整份规则会被第二层直接连根拔起丢弃（整条蒸发）；
- 如果只改第二层 Token 预算：文件早在第一阶段加载时就被切成 24KB 残卷，截断依旧发生。
- **因此，必须双层纯数值同步放宽！**

## 四、 修复方案：双层纯数值等长机器码替换

### 1. 设计原则
- **零控制流破坏 (Zero Control Flow Disruption)**：
  绝不改动任何 `cmp`、`jle`、`jmp`、`jne` 跳转逻辑，不改变任何指令长度，仅仅将 32 位立即数放大；
- **纯数值放宽目标**：
  - **第一层字节门禁**：从 `24,000` 字节（`0x5DC0`）放大到 **`500,000` 字节（`0x7A120`）**，满足 500KB 超大规则；
  - **第二层 Token 门禁**：从 `20,000` Tokens（`0x4E20`）放大到 **`200,000` Tokens（`0x30D40`）**，满足 20 万 Token 级别超大规则集。

### 2. 12 处修改点机器码精确对照表

#### 第一层：单文件物理字节上限放宽（4 处）
| 序号 | 汇编指令模板 | 原机器码 (24,000 = `0x5DC0`) | 补丁机器码 (500,000 = `0x7A120`) | 语义功能 |
|:---:|:---|:---|:---|:---|
| **B1** | `mov ecx, imm32` | `b9 c0 5d 00 00` | `b9 20 a1 07 00` | 规则裁剪入口 1 字节限额 |
| **B2** | `mov ecx, imm32` | `b9 c0 5d 00 00` | `b9 20 a1 07 00` | 规则裁剪入口 2 字节限额 |
| **B3** | `mov ecx, imm32` | `b9 c0 5d 00 00` | `b9 20 a1 07 00` | 换行截断与 TruncatedContent 限额 |
| **B4** | `cmp rax, imm32` | `48 3d c0 5d 00 00` | `48 3d 20 a1 07 00` | 文件 Body 字节门禁比较上限 |

#### 第二层：Token 预算与安全 Clamp 放宽（8 处）
| 序号 | 汇编指令模板 | 原机器码 (20,000 = `0x4E20`) | 补丁机器码 (200,000 = `0x30D40`) | 语义功能 |
|:---:|:---|:---|:---|:---|
| **T1** | `mov r9d, imm32` | `41 b9 20 4e 00 00` | `41 b9 40 0d 03 00` | User Rules 默认分配 |
| **T2** | `mov edx, imm32` | `ba 20 4e 00 00` | `ba 40 0d 03 00` | Workspace Rules 默认分配 |
| **T3** | `cmp rbx, imm32` | `48 81 fb 20 4e 00 00` | `48 81 fb 40 0d 03 00` | User Rules Clamp 比较 |
| **T4** | `mov edx, imm32` | `ba 20 4e 00 00` | `ba 40 0d 03 00` | User Rules Clamp 钳位赋值 |
| **T5** | `cmp rbx, imm32` | `48 81 fb 20 4e 00 00` | `48 81 fb 40 0d 03 00` | Workspace Rules Clamp 比较 |
| **T6** | `mov edx, imm32` | `ba 20 4e 00 00` | `ba 40 0d 03 00` | Workspace Rules Clamp 钳位赋值 |

## 六、 自动化工程落地与操作规范

### 1. 扫描与标定新版本
当遇到官方更新发布新版本时，运行：
```bash
node scripts/scan-patch-sites.js <官方出厂备份路径>
```
脚本会自动在 `.text` 代码段中扫描这 12 处指令模式，输出新版本的精确 FileRaw 偏移量。

### 2. 执行补丁落地
运行针对当前版本的修补脚本（如 v1.4.6）：
```bash
node scripts/patch-agy-1.4.6.js
```
脚本自动执行：
1. 校验出厂原版备份（`agy.exe.1.4.6.orig`）的存在性与 SHA256 哈希；
2. 逐一验证 12 处预定偏移的机器码是否 100% 匹配官方原值；
3. 将修改写入临时文件；
4. 采用 Windows **原子重命名**（`rename` 正在运行的旧文件 -> 写入新文件）安全替换 `C:\Users\<user>\AppData\Local\agy\bin\agy.exe`。

### 3. 逐字节二次核验
运行：
```bash
node scripts/verify-patch-1.4.6.js
```
确保磁盘上的可执行文件 12 处字节替换 100% 正确且文件体积保持 0 偏差。

## 七、 规则完整性金丝雀探针（EOF Anchor）

为防止未来版本更新覆盖或规则意外截断，在工作区规则（`F:\Git\CLAUDE.md` / `GEMINI.md`）末尾统一部署**规则完整性金丝雀**：

```markdown
## 规则完整性金丝雀（EOF Anchor）

- **校验暗号**：`AGY-CANARY-OMEGA-483`
- **行为契约**：当用户询问暗号、金丝雀或末尾校验码时，必须原样回答该字符串。若在当前会话的系统提示词或 `<RULE[...]>` 块末尾检索不到本项，说明规则已被底层物理截断，必须主动向用户报告并重新通过文件工具读取完整规范。
```

- **验证方式**：用户在会话中只需发送指令“金丝雀”，Agent 若能从上下文末尾读取暗号并原样复述，即证明 500+ 行规则 100% 全量注入；若提示词末尾丢失该项，Agent 会立即向用户发出截断警报。
